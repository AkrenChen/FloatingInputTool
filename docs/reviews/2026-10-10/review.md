# FloatingInputTool 代码与体验审查

日期：2026-10-10。范围：目标、全部现有设计文档、根目录计划与记录，重点审查 Tauri 实现；AHK 仅作为历史行为原型核对。

## 判断

项目真正目标是随时呼出、快速记录、可靠保存、不打断工作。现有实现已具备单实例、快捷键事务、原子替换、草稿恢复和背景降级，但窗口控制及设置编辑仍有多个明确缺陷。建议保留 Tauri，先修状态与数据一致性，再调整信息架构和视觉。

这是代码审查，未复现用户现场的界面错乱；以下静态确定的问题不能直接等同于所有现场故障的根因。

## 优先修复

### P0：草稿写入缺少统一顺序

代码：`tauri-app/src-tauri/src/lib.rs:289,337,349,747`。

每次草稿更新创建线程，等待 150ms 后检查 generation。flush 只在克隆草稿时持锁，磁盘写入不受同一写入锁保护。旧 flush 已拿到快照后，clear 可以写入空草稿，随后旧 flush 再落盘，复活被丢弃或已保存的文本。generation 检查无法取消已经开始的写入。

建议：独立的单一草稿写入队列或工作任务，统一 update、flush、clear 的顺序。快照带 revision，clear 也作为有序操作；写入失败保留待重试状态并反馈给用户。不要每次按键创建 OS 线程。

验收：可控地延迟旧写入，执行 clear 或新更新后释放旧操作，最终磁盘仍是最新版本；覆盖保存、丢弃、退出、重启。

### P0：保存中的输入与提交没有明确边界

代码：`tauri-app/src/App.tsx:586,634,763`，`tauri-app/src-tauri/src/lib.rs:747`。

保存请求提交当前字符串，编辑器仍可输入；成功响应无条件 setDraft('')，会抹掉提交后新增的输入。Rust 同样无条件清空当前草稿。前端仅靠 React state 禁用重复保存，没有提交 id 或后端去重机制。另外 Enter 保存处理没有检查 IME composition，中文输入法确认候选时存在提前提交风险。

建议：保存绑定不可变的文本、目标 id、草稿 revision 和提交 id；成功只清除已提交版本。可以先采用保存期间短暂锁定编辑及目标切换的简单方案。输入法组词时禁止提交。

验收：延迟保存响应后继续输入，不丢新增内容；快速连续提交不重复写入；中文候选确认不触发保存；写入失败保留草稿。

### P1：恢复普通窗口漏恢复缩放能力

代码：`tauri-app/src-tauri/src/lib.rs:866,990,2100`。

贴边流程 set_resizable(false)，Capture 经 restore_main_window_to_normal 恢复位置和模式，却没有 set_resizable(true)。这是可以直接从代码确认的缺陷。

建议：进入任何模式时完整设置位置、缩放、圆角、可见性及焦点规则，不能依赖前一个模式恰好留下正确属性。

验收：贴边后快捷键呼出仍能缩放，重复 100 次无窗口属性漂移。

### P1：窗口转换由多个来源并发驱动

代码：`App.tsx:71,305,365,503,660`，`lib.rs:933,1106,1706,1811,1928`。

前端鼠标计时器、光标轮询、编辑器焦点、后端移动事件、快捷键、延迟焦点重试都能推动转换。动画逐帧修改原生位置并 sleep，没有统一转换锁和取消机制；移动事件每次新建线程。generation 只在等待结束检查一次，后续等待鼠标松开与动画仍可遇到新命令。展开先通知前端模式再完成几何，收起则先动画再通知，转换顺序也不统一。

建议：Rust WindowController 成为状态唯一来源，所有窗口意图经过一个队列，加入 transitioning 状态和转换序号；Capture 取消旧收起及延迟焦点任务。React 只渲染状态与发送意图。先验证无动画转换，再加入可取消动画，避免同步 sleep 堵住调用链。

验收：快速 Capture/Hide、拖拽时呼出、展开时打开设置、双屏不同 DPI、显示器移除、锁屏恢复都不会错误收起或停在过期位置。

### P1：设置更新覆盖其他未保存编辑

代码：`tauri-app/src/SettingsApp.tsx:166`。

app-config-changed 无差别重置 targets、快捷键输入、模板输入和自定义主题草稿。复现路径：修改模板但不保存，再切换主题，模板编辑会被旧配置覆盖。保存任一设置也会广播这个事件。

建议：拆分 persistedConfig 和 editableDraft；按区域维护 dirty 状态，外部更新仅更新没有修改的字段，冲突显示明确提示。避免用同一组 state 表示已保存值和编辑值。

验收：编辑模板后保存主题或快捷键，模板内容仍在；取消只撤销当前区域。

### P1：配置落盘失败后内存已改变

代码：`tauri-app/src-tauri/src/lib.rs:369,398,422,479,511,701,724`。

多数 setter 先改共享配置，再执行 save_app_config，失败直接返回。UI 显示保存失败，但应用可能继续使用新内存配置，重启又回到旧值。快捷键更新有专用事务，但其他设置没有同等保障；快捷键事务克隆整个配置后再提交，也需要纳入统一配置序列，避免与其他更新覆盖。

建议：统一 ConfigStore 的 validate → 构造候选 → 持久化成功 → 发布内存与事件流程。帮助文档写入失败不应把已经成功的配置写入伪装成完全失败；区分事务失败和通知失败。

验收：模拟无写权限、磁盘失败、事件失败，返回状态和实际配置一致；并发修改互不覆盖。

## 布局问题

### 默认设置宽度就进入窄屏分支，但行布局没有适配

代码：`lib.rs:1324`，`App.css:977,1237,1253,1380`。

设置默认宽 560、最小 500，媒体查询在 <=680 添加 14px 外层 padding。快捷键行仍为 88px + 至少150px + 保存按钮 + 至少160px + 三个8px间隙，尚未计按钮宽度就需422px。最小窗口下内容宽度进一步被边距压缩，存在横向溢出；默认宽度也很拥挤。目标列表同样用固定多列下限。

建议：快捷键用「动作名 / 录制控件」两列，当前生效信息放下一行；目标用两行条目，上行名称与默认标记，下行路径与浏览按钮。窄宽度真正切换布局，不只是增加 padding。

### 反馈出现改变 Grid 子节点数量

代码：`App.css:697`，`SettingsApp.tsx:1036`。

设置定义三行 auto / 1fr / auto；实际有 header、content、可选 feedback、footer 四个直接子节点。反馈出现时 footer 被安排到隐式第四行，内容区高度随消息改变。

建议：明确命名 header、content、status、footer，保留固定状态区域；短反馈放在对应控件旁，长错误可展开详情。主窗口的长错误也要限制高度，避免挤压编辑区。

### 原生和 CSS 圆角不是同一标准

代码：`lib.rs:1192`，`App.css:1,689`，`index.css:24`。

当前原生用 Windows 标准圆角，CSS 多处固定 22px；历史记录明确两者半径不同。原生 Acrylic 覆盖范围与 WebView 裁剪仍可能出现角落材质不一致。没有现场截图，不能确认它就是这次「变乱」的表现。

建议：统一圆角 token 和平台策略；设置窗口优先使用稳定不透明背景，主窗口保留 Acrylic 作为外观选项，并提供可选的稳定不透明模式。不要继续叠加原生区域裁剪补丁。

## 设置应该如何组织

信息架构建议：

| 页面 | 内容 | 默认展开程度 |
| --- | --- | --- |
| 记录 | 保存位置、目标管理 | 常用内容直接可见 |
| 快捷键与行为 | 呼出、隐藏、目标切换、提交方式、贴边开关 | 标准布局；贴边细参数进入高级 |
| 外观 | 跟随系统/浅色/深色、自定义、背景效果、语言 | 自定义细项按需展开 |
| 高级与诊断 | 模板、贴边延迟/阈值、日志入口、版本与署名 | 默认收起 |

模板编辑不应排在快捷键和基础外观之前。主题选择用紧凑的单选或分段控件；透明度用滑杆和数值，避免四张大卡片堆叠。取消应是中性操作，红色保留给删除与丢弃。

保存语义统一：普通单选和开关立即保存并显示局部结果；目标、模板、自定义配色进入明确编辑模式，提供固定的保存/取消操作。避免多个长得一样的 Save、Cancel 分散在长页面。设置关闭通过 Rust 统一完成，收尾预览、未保存状态和主窗口恢复。

这是提议的信息架构，尚未作为实现规格确认；不会直接改功能。

## 重构边界与路线

当前 lib.rs 约2400行，SettingsApp 约1100行，App 约900行。问题不是行数本身，而是窗口、存储、快捷键、配置和视图状态揉在同一入口中。

建议边界：Rust 分成 WindowController、DraftStore、ConfigStore、NoteWriter、HotkeyManager；React 分出捕获编辑器、目标切换器、设置分类面板与统一 Tauri 订阅 hook。NoteWriter 串行化本应用的读改写，并检测外部文件变化；原子替换只能防止半文件，不能防止 Obsidian/同步软件的同时编辑被覆盖。外部竞争应显式报冲突并保留草稿，不能承诺简单重试绝对安全。

三种路线：

1. 推荐：保留技术栈，按数据可靠性 → 窗口状态 → 布局与设置组织分批整改。范围可控，可逐批验证。
2. 快速止痛：提供关闭贴边动画、禁用背景效果的稳定配置，先修明确布局和设置编辑问题。能缓解体验，不能替代草稿/配置一致性修复。
3. 全面重写：重新实现全部 UI 与原生窗口逻辑。验证成本最高，当前没有证据表明框架是根因，不推荐。

不要为了拆文件引入复杂架构；先提取最容易独立验证的状态转换和存储边界。
